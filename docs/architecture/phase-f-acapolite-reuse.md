# Phase F Acapolite reuse classification

Per [`acapolite-reuse-strategy.md`](acapolite-reuse-strategy.md)'s required process. The paid-campaigns module (`ad_campaigns`/`ad_sets`/`ads`/`ad_creatives`/`ad_publish_operations`/`ad_campaign_metrics` and their edge functions) was originally built as "Phase 6," inspecting the Acapolite Campaign/Social platform as its source implementation - this document records that classification for the areas Phase F's brief specifically calls out, since it predates the durable per-phase documentation convention established afterward.

| Acapolite source area | Classification | Notes |
|---|---|---|
| Meta provider abstraction (Graph API HTTP calls) | Reuse with workspace adaptation | `_shared/ad-providers/metaMarketingApi.ts` mirrors Acapolite's separation of pure payload builders from fetch-performing functions, but resolves a workspace-scoped Vault token via `get_workspace_integration_secret()` instead of a global app-level token. |
| Error classification | Reuse with workspace adaptation | `metaAdsErrorClassifier.ts` keeps Acapolite's actionable-category shape (temporary vs. permanent, with a specific policy-review category) but as a clean, campaign-module-local hierarchy - not shared with Content's own classifier, matching the "paid stays distinct from organic" rule. |
| Publish-operation / idempotency pattern | Reuse with workspace adaptation | The `ad_publish_operations` + `idempotency_key` unique-constraint + atomic status-claim pattern mirrors Content's own `content_publish_attempts` idempotency design (itself adapted from Acapolite) - proven twice now (Content, Campaigns) as the right shape for "a retry must never double-act." |
| Media/platform-variant selection for creatives | Reuse unchanged (via Content module) | `ad_creatives.media_asset_id`/`platform_variant_id` reference the *same* `content_media_assets`/`content_platform_variants` rows Content already manages - no separate paid-media library, no duplicated binaries. |
| Connection-health checks | Reuse with workspace adaptation | `ad-connection-health` performs the same category of live token/resource checks Acapolite's admin health page does, scoped to one workspace's integration rather than the single global connection. |
| Activity logging | Rewrite because of documented incompatibility | Not a separate `ad_campaign_activity` table (which Acapolite-style single-tenant systems often use) - every campaign action logs into the same shared `workspace_activity_log` every other StabiFlow module uses, per the durable "don't fork a per-module audit trail" rule. |
| Campaign structure (objective/targeting/creative UI patterns) | Reuse with workspace adaptation | The Campaign Builder's step flow (goal -> account -> audience -> budget -> creative -> review -> publish) follows Acapolite's proven guided-builder UX, generalized to StabiFlow's multi-workspace Ad Account/Page/Instagram selection instead of one fixed account. |
| Tax-specific campaign content, single-company assumptions, hardcoded Meta resources | Intentionally left behind | Never ported - see the schema migration's own header comment and the durable prohibitions in `acapolite-reuse-strategy.md`. |

## Phase F's own additions (not a reuse question - net-new)

Click-to-WhatsApp destination support (`ad_creatives.whatsapp_number_id`, the `metaMarketingApi.ts` creative-payload whatsapp branch, `adReadiness.ts` validation) and the mock Meta Ads provider (`metaMarketingApiMock.ts`) used for safe, spend-free saga testing are both new in this phase - the underlying schema hooks for WhatsApp destinations already existed in the Phase 6 schema (`destination_type` enum, `ad_creatives.whatsapp_number_id` column and its workspace-consistency trigger) but were never wired up end to end; this phase closes that gap. See the Phase F completion report for what was found already complete versus what was actually built.
